## 1. Задача

Расширить **существующий** Python-сервер OCR Торгсофт → 1С для приёма актуального полного снимка остатков 1С, контроля его целостности и отдачи статуса свежести. Не переписывать OCR, веб-форму обработки чеков, семантическое сопоставление и подтверждённые соответствия товаров.

Новые правила использования кнопок находятся **на стороне 1С**, однако Python должен обеспечить два сервиса: `GET` статуса и `POST` полного снимка. После нажатия первой кнопки 1С **сначала запускает OCR и открывает браузер**, а затем независимо проверяет статус остатков; Python **не должен требовать завершения синхронизации для старта OCR**.

## 3. Настройка срока свежести

Добавить в **единый существующий `.env`**:

```dotenv
STOCK_TTL_HOURS=1
```

Параметр в **часах**, исходное рекомендуемое значение — `1`. Проверять допустимость положительного значения. Срок свежести считать **только от `stock_as_of`** (времени бухгалтерского среза из 1С). Время получения файла Python не влияет на свежесть и хранится при необходимости лишь в журнале сервера. Даты считать timezone-aware, сравнивать с текущим временем сервера по UTC; хранить ISO 8601 с часовым поясом.

Если валидного снимка для указанной пары организация/склад нет, вернуть `needs_update=true`, `status="missing"`. Если срок исчерпан — `needs_update=true`, `status="expired"`; иначе `needs_update=false`, `status="fresh"`. `ttl_remaining_seconds` — целое количество секунд, для устаревших значений `0`.

Никакого 5-минутного cooldown после ошибки, автоматических очередей и сложных механизмов блокировок: сейчас один оператор. Не делать приложение чрезмерно сложным.

## 4. API статуса

**GET `/api/1c/stock-sync/status?organization_id={UUID}&warehouse_id={UUID}`**.

Авторизация — действующий `X-API-Key` (либо совместимый установленный в проекте механизм). Ответ HTTP 200 при успешно определённом статусе:

```json
{
  "status": "fresh",
  "needs_update": false,
  "organization_id": "11111111-1111-4111-8111-111111111111",
  "warehouse_id": "22222222-2222-4222-8222-222222222222",
  "snapshot_id": "b3d2a811-9d24-4dd5-ae8c-742cf4b289ab",
  "stock_as_of": "2026-11-03T09:00:00+05:00",
  "ttl_remaining_seconds": 2520,
  "record_count": 3701
}
```

Идентификаторы и количество здесь иллюстративные. При отсутствии производственного JSON либо при несовпадении пары организация/склад — `status="missing"`, `needs_update=true`, `snapshot_id=null`, `stock_as_of=null`, `record_count=0`, `ttl_remaining_seconds=0`. При истечении TTL — `status="expired"`, `needs_update=true`, `ttl_remaining_seconds=0`. При повреждённом существующем JSON — вернуть ошибку сервера/валидации и **не переключаться молча на Excel** с ложным статусом «fresh».

Коды: `400/422` для некорректных параметров, `401` для отсутствия авторизации, `500` для внутренней ошибки. Отсутствие ответа или ошибочный HTTP не должно восприниматься как `needs_update=false`.

В 1С при `fresh` показывать только дату среза и оставшийся срок в понятных часах/минутах. Строку «Срок актуальности — 60 минут» не выводить. При недоступном статусе 1С показывает обычное немодальное сообщение «OCR: Статус обновления остатков не получен.», не отправляет остатки и не прерывает OCR.

## 5. API загрузки: один POST и согласованная структура файла

**POST `/api/1c/stock-sync`**, весь полный снимок передаётся **одним JSON HTTP-запросом**. Допустимый размер до **10 МБ** (конфигурируемый), без порционной загрузки и дополнительных commit-запросов.

Заголовки:

```http
Content-Type: application/json; charset=utf-8
X-API-Key: <ключ>
X-Content-SHA256: <64 символа hex SHA-256 тела>
```

Тело HTTP **и содержимое производственного файла после успешной проверки** имеют одну структуру:

```json
{
  "schema_version": "1.0",
  "snapshot_id": "b3d2a811-9d24-4dd5-ae8c-742cf4b289ab",
  "source": "1c",
  "database_id": "1c-alatau",
  "organization": {
    "id": "11111111-1111-4111-8111-111111111111",
    "name": "ИП Алатау"
  },
  "warehouse": {
    "id": "22222222-2222-4222-8222-222222222222",
    "name": "Основной склад"
  },
  "stock_as_of": "2026-11-03T09:20:00+05:00",
  "record_count": 2,
  "items": [
    {
      "uuid": "33333333-3333-4333-8333-333333333333",
      "code": "00000003861",
      "name": "Профиль стеновой 100/50",
      "unit": "шт",
      "service": false,
      "stock_quantity": "432.000",
      "stock_amount": "2478254.40",
      "accounting_price": "5736.70",
      "account_code": "1330"
    },
    {
      "uuid": "44444444-4444-4444-8444-444444444444",
      "code": "00000005924",
      "name": "Правило алюминиевое 3 м",
      "unit": "шт",
      "service": false,
      "stock_quantity": "0.000",
      "stock_amount": "0.00",
      "accounting_price": null,
      "account_code": "1330"
    }
  ]
}
```

Пример условный: ID, товары, суммы и даты не являются реальными остатками. **В JSON нет отдельного времени получения/сохранения сервером Python**: для актуальности предусмотрен только `stock_as_of`. При желании факт получения фиксировать в служебном журнале, вне JSON.

Контракт:

- `database_id`, `organization.id` и `warehouse.id` определяют источник и принадлежность снимка; во всех запросах статуса UUID должны совпадать с текущей парой.
- `snapshot_id` — UUID целого снимка, неизменный при безопасном повторе одного запроса.
- `uuid` — UUID номенклатуры 1С; не терять существующий `code` и не отождествлять чужие товары по похожему наименованию. `code` — строго строка, сохраняющая ведущие нули.
- `name`, `unit`, `service` сохраняются для каталога; нулевые остатки товаров обязательно включаются, группы исключаются; услуги при включении: `service=true`, числовые складские поля `null`.
- `stock_quantity`, `stock_amount`, `accounting_price` — `Decimal` в виде строки либо `null`. `null` означает неизвестно/не применимо, `"0.000"` — подтверждённый ноль. Допускать отрицательные учётные остатки; не подменять ошибку расчёта нулём.
- `account_code` — счёт БУ строкой либо `null` при отсутствии; данные по одному товару и складу не дублировать в массиве.
- Для расчёта количества, стоимости, даты среза на стороне 1С использовать общий существующий бухгалтерский адаптер. Новый JSON — **полный каталог**, не файл поправок к старому Excel.

Если исходник 1С не располагает отдельной учётной стоимостью или счётом — поле передавать `null`, а не вычислять недостоверные значения. Конкретные правила бухгалтерского расчёта согласуются на стороне 1С.

## 6. Контроль целостности SHA-256

1. Прочитать **исходные байты HTTP-тела** в пределах лимита, не преобразовывая и не пересериализуя их для контроля.
2. Вычислить SHA-256 исходных байтов, сравнить с `X-Content-SHA256` (`hmac.compare_digest`).
3. При несовпадении — HTTP `422` и удаление `.tmp` (если создан); рабочий JSON не менять.
4. При совпадении проверить UTF-8 без BOM, синтаксис JSON, `schema_version`, UUID, структуру пары организация/склад, `record_count == len(items)`, уникальность UUID/кодов, дату с часовым поясом, обязательные поля и числовые значения `Decimal`.
5. Проверить целостность уже записанного `.tmp` — например, перечитать байты и повторно сверить SHA-256, до переименования.
6. SHA-256 не является аутентификацией: использовать API-ключ; HTTPS требуется при доступе вне доверенной LAN.

Нельзя добавлять или менять поля в JSON после проверки SHA-256: рабочий файл содержит **ровно проверенный и принятый payload**.

## 7. Размещение, приоритет чтения и безопасная замена файла

**Единственный производственный JSON-файл:**

`Data/reference/1c_ref/catalog_1c_current.json`

**Файл во время приёма/проверки:**

`Data/reference/1c_ref/catalog_1c_current.json.tmp`

Относительные пути отсчитываются от корня Python-проекта. Имя постоянное, без даты в названии; дата среза находится только внутри JSON.

### Правило выбора источника каталога и остатков

1. Если `catalog_1c_current.json` существует и валиден — **первично использовать его** для номенклатуры, количества, учётной цены и бухстоимости; Excel/CSV не смешивать с ним как с параллельным актуальным источником.
2. Если рабочего JSON **нет** — использовать действующую загрузку Excel/CSV из `Data/reference/1c_ref` (с исторической датой, взятой из имени Excel, без искусственного обновления времени).
3. Если рабочий JSON **есть, но повреждён** — вывести диагностическую ошибку, **не подменять автоматически старыми Excel-остатками**.
4. Файл `.tmp` не участвует в подборе или проверке свежести ни при каких условиях.
5. Если в папке несколько Excel-файлов, сохранить действующие правила чтения Excel только для fallback; JSON всё равно имеет приоритет целиком.

### Порядок приёма

1. После проверки авторизации принимать тело в `catalog_1c_current.json.tmp` в той же директории. Во время передачи текущий `catalog_1c_current.json` остаётся рабочим.
2. Сверить SHA-256 HTTP-байтов, парсинг и всю структуру, количество и уникальность товаров. Если проверка не пройдена — удалить `.tmp`, вернуть HTTP 422, прежний рабочий файл не затрагивать.
3. Записать проверенные байты на диск целиком, `flush` + `os.fsync`. Вновь сверить файл с исходным payload.
4. После всех проверок **атомарно** заменить рабочий файл: `os.replace(tmp_path, production_path)`; оба файла находятся на одном файловом томе.
5. После успешного переключения обновить/сбросить кэш справочника. Все новые обращения должны читать новую версию; уже начатый OCR не блокировать и не переписывать его результаты задним числом.
6. Вернуть HTTP 200 **только после успешного переключения и обеспечения чтения нового снимка**. При ошибке до `os.replace` удалить `.tmp`, старый JSON остаётся неизменным. Повреждённый файл не публиковать.
7. После нормального завершения `.tmp` отсутствует. При старте приложения оставшийся после аварийной остановки `.tmp` не использовать и удалить/очистить безопасно.

**Идемпотентность:** если уже опубликован JSON с тем же `snapshot_id` и тем же SHA-256 — вернуть успешный ответ без повторной записи. Тот же ID с другим содержимым — `409`. Не допускать замены более нового `stock_as_of` старым. Очереди, распределённые блокировки и 5-минутный cooldown не нужны (один оператор).

**Граница одного файла:** текущая договорённость — один активный снимок. Если организация/склад в запросе статуса не совпадают с метаданными файла, вернуть `missing` для этой пары, не использовать чужие остатки. При попытке POST для другой пары валидировать происхождение и не смешивать товары разных складов; при необходимости будущего многоскладского хранения согласовать его отдельно.

## 8. Подтверждение загрузки

HTTP 200 возможен **только после атомарной публикации производственного JSON**:

```json
{
  "status": "committed",
  "snapshot_id": "b3d2a811-9d24-4dd5-ae8c-742cf4b289ab",
  "organization_id": "11111111-1111-4111-8111-111111111111",
  "warehouse_id": "22222222-2222-4222-8222-222222222222",
  "received_count": 3701,
  "integrity": "verified",
  "sha256": "<64 символа hex хеша HTTP-тела>",
  "stock_as_of": "2026-11-03T09:20:00+05:00"
}
```

`received_count` всегда равно `record_count` принятого снимка; приведённые значения условные. Время приёма Python в ответе и в сохранённом JSON **не требуется**.

Коды отказа: `400` запрос, `401` авторизация, `409` конфликт или устаревший срез, `413` превышен размер, `422` невалидное содержимое/хеш, `500` ошибка записи. Ошибки — JSON с `code` и `message`, без стектрейсов/секретов. При неизвестном статусе после тайм-аута 1С вправе повторить **точно то же тело с тем же `snapshot_id`**; сервер обязан ответить идемпотентно.

## 9. Интеграция с текущим каталогом, OCR и матчингом

- В текущей GitHub-ветке `App/invoicing/catalog_1c.py` читает Excel/CSV из `Data/reference/1c_ref`, возвращает индекс `items/by_id/by_code/by_name`, кэширует по сигнатуре файлов. **Доработать этот модуль**, не создавать параллельный независимый каталог: JSON должен давать тот же внешний контракт и индекс поиска.
- `App/invoicing/transform_candidates.py` содержит исторические `stock_snapshot`/`stock_date`. При наличии рабочего JSON **не выдавать эти старые поля за текущие**: кандидаты должны получать свежие `stock_quantity`/`stock_as_of` из единого актуального каталога; сохранить ранги и смысловые сопоставления.
- `App/invoicing/invoice_service.py` и путь построения счёта должны инвалидировать зависимые кэши/ревизии при новой версии JSON. При этом подтверждённые связи и ручной mapping не переписывать.
- Стабильность идентификаторов обязательна: существующие `catalog_id`/хеши по коду и подтверждённые ссылки не должны перестать разрешаться после перехода Excel→JSON; при наличии UUID хранить его как явное поле, обеспечить совместимый поиск по старому коду/id.
- OCR запускается до проверки свежести, синхронизация его не блокирует; для выбора кандидатов использовать целостный снимок, не смесь до/после переключения. Итоговое наличие товара перед выставлением счёта по-прежнему контролирует 1С.
- Если JSON отсутствует, оставить Excel fallback со старой реальной датой; это не должно маскироваться как «свежий» снимок.
- При успешной загрузке проверять, что `/api/catalog-1c` и выдаваемые кандидаты используют **новые** значения, а не только то, что файл появился на диске.
- Сохранять действующий OCR, API `/tasks` и пользовательское подтверждение соответствий; не переобучать их автоматически.

## 10. Веб-интерфейс и сообщения

- Основной операторский интерфейс OCR и кнопки в нём **не менять**, если это не необходимо для чтения данных.

8. Переключение каталога Excel→JSON не ломает прежние `catalog_id`, сохранённый mapping, поиск кандидатов и бухгалтерские поля; после следующего GET кандидатов значения количества изменились.
9. Регрессия `/tasks`, запуска OCR до получения статуса и до POST, независимой выдачи результата. Поскольку изменяется путь кандидатов, при наличии реальных фото выполнить реальную OCR-регрессию наряду с синтетической. При недоступности эталонов отметить честный SKIP.
10. Проверить, что рабочий JSON и API статуса не содержат дополнительного времени приёма Python; необязательный журнал приёма не участвует в TTL.

Сохранить отчёт PASS/FAIL/SKIP. Никаких отдельных тестовых заданий пользователю.

## 12. Результат от Python-разработчика

Передать один ZIP с одной корневой папкой эксперимента, где находятся:
