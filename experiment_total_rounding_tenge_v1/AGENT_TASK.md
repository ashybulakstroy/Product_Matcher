# Задание Codex — Total Rounding Tenge v1.0

**Эталон репозитория при разработке:** `ashybulakstroy/Product_Matcher`, ветка `main`, коммит `9ced832c05bc3e8f8839e4455d8fba6a8fd2feb4` (сверен 14.11.2026). Перед установкой перепроверить текущую ветку. Выполнять этапы **последовательно**.

## Этап 0. Диагностика

1. Проверить фото и эталон `fixtures/receipt_16_rows.json`; не изменять эталон ради положительного результата.
2. Сохранить исходный `receipt.json`, `calculation` и контрольную сумму `App/ocr/receipt_editing.py`.
3. Проверить отсутствие локальных изменений в затрагиваемых строках; если есть — не перезаписывать, предложить конфликтный diff.

## Этап 1. Подключить эксперимент

1. Запустить `pytest -q experiment_total_rounding_tenge_v1/tests` и `run_fixture.py`.
2. Выполнить `install.py --preview`, изучить `data/output/receipt_total_rounding/preview.diff`.
3. Если нет конфликтов — `install.py --apply`. Изменить лишь `App/ocr/receipt_editing.py`, создать `App/ocr/receipt_rounding.py`.
4. Ни один рабочий файл `App` не должен импортировать `experiment_total_rounding_tenge_v1`.

## Этап 2. Синтетические проверки и блокировка

1. Точный итог без округления должен сохранять прежнее поведение.
2. `80812.65 → 80813.00` принимается **только при точном совпадении с проверенной формулой**.
3. Проверить альтернативу округления каждой строки, отсутствие цен/количеств, неверные целотенговые суммы, печатные тиыны, неправильный НДС.
4. Сравнить состояние `quantity`, `price`, `line_total` и `*_raw` до/после: никаких изменений.
5. Проверить контракт для веб-интерфейса и счёта: `computed_total`, `exact_computed_total`, `rounding_adjustment`, `expected_total`. Для PDF убедиться, что счёт на 80 813 ₸ сохраняет согласованность строк; если генератор корректирует отдельную строку, сообщить об этом явно. **Не расширять эту задачу на генератор счета без отдельного подтверждения.**
6. При любом падении теста **остановить расширение работ**, локализовать проблему и повторить весь этап 2. Не удалять тесты.

## Этап 3. Реальные испытания

1. `run_fixture.py --full-ocr` на включённой фотографии и реально установленной ONNX-модели.
2. Проверить 16 строк товара + 1 НДС; цену `835.71` и количество `15` строки №14; 11 147 ₸ НДС; 80 813 ₸ печатного итога.
3. Запустить регрессию по доступным реальным чекам, особенно со стандартным точным итогом, с целотенговой арифметической ошибкой и неполными числовыми полями.
4. Если OCR ошибся в другом поле, не выдавать неуспех за проблему округления. Зафиксировать отдельно.

## Этап 4. Отчёт

Создать `data/output/receipt_total_rounding/REPORT.md` с исходной и новой арифметикой, списком файлов, числом успешных/неуспешных/пропущенных тестов, результатом OCR на фото, проверкой счёта и рисками. При отказе — исполнить `--restore` при неизменных SHA256. **Не объявлять эксперимент полностью успешным, пока не пройдён реальный чек и регрессия.**
