# Эксперимент: Total Rounding Tenge v1.0

**Цель:** устранить ложное красное предупреждение OCR-чека, если точная сумма строк с тиынами математически согласуется с **напечатанной целой суммой в тенге** по подтверждаемому правилу округления. Не добавлять произвольный допуск ±1 ₸ и не исправлять цифры OCR автоматически.

## Контрольный чек

В `fixtures/` находятся:

- `receipt_original_2142822991.png` — исходная фотография чека (13.11.2026, заказ №2142822991);
- `app_mismatch_0_35.png` — скриншот ложного предупреждения;
- `receipt_16_rows.json` — **вручную сверенные с фото** 16 товарных строк, отдельная строка НДС и контрольные суммы.

Результат сверки оригинала:

| Проверка | Сумма |
|---|---:|
| Товары (точно до тиына) | 69 665,65 ₸ |
| НДС (напечатан, 16%) | 11 147,00 ₸ |
| Математическая сумма | 80 812,65 ₸ |
| Напечатано в чеке | 80 813,00 ₸ |
| Корректировка округления | +0,35 ₸ |

Строка 14: `15 × 835,71 = 12 535,65 ₸`. До целого тенге она округляется в `12 536 ₸`. На этом образце совпадают **две** возможные схемы: (a) округление общего итога до тенге и (b) сумма целотенговых округлений каждой строки. Это **не доказывает, какая именно схема реализована в Торгсофте**; обе формулы проверяются отдельно и фиксируются в диагностике.

## Архитектура

Изменяются **только**:

- `App/ocr/receipt_editing.py` — подключается отдельный расчётный валидатор и его диагностические поля;
- `App/ocr/receipt_rounding.py` — новый модуль на стандартной библиотеке `decimal`.

В рабочем `App` **нет импортов из экспериментального каталога**. Не изменяются RapidOCR, Tesseract, модели, геометрия, распознавание цен, процент НДС, `.env`, формулы проверки НДС, счета 1С или исходные значения строк. Новые зависимости устанавливать не нужно.

Проверка сначала сравнивает **точную сумму до тиына**. Если она не совпала, рассматриваются только два математически определённых способа округления `ROUND_HALF_UP` до **целого тенге**:

1. `ROUND_HALF_UP(сумма_строк, 1 ₸)`;
2. `сумма(ROUND_HALF_UP(каждая_строка, 1 ₸))`.

Округлённый вариант разрешён **только** если напечатанный итог — целое число тенге и хотя бы одна реальная сумма строки имеет дробную часть. Если формула не даёт *точно* напечатанную сумму — чек остаётся с ошибкой. Отсутствующая цена, количество, отсутствующий итог и ошибка НДС **никогда** не маскируются округлением.

В `calculation` сохраняются:

- `computed_total` — подтверждённый итог для интерфейса: `80813.00`;
- `exact_computed_total` — исходная точная сумма: `80812.65`;
- `rounding_mode` — применённая формула (или `exact`/`unverified`);
- `rounding_adjustment` — `0.35`;
- `rounding.matched_modes`, `rounding.fractional_rows`, `rounding.candidates`, `exact_difference` — аудит.

Числа `quantity`, `price`, `line_total`, `*_raw`, а также НДС остаются неизменными. Дополнительно проверить, как существующий генератор счета и PDF представляет небольшую корректировку и обеспечивает сумму строк = итогу счета: сам эксперимент счета не перерассчитывает и не меняет.

## Использование в Windows / PowerShell

Распаковать ZIP **одной папкой** `experiment_total_rounding_tenge_v1` в корень проекта (рядом с `App` и `data`). Работа из корня проекта:

**1. Предварительные тесты и контрольная математика**

```powershell
.\.venv\Scripts\python.exe -m pytest -q experiment_total_rounding_tenge_v1\tests
.\.venv\Scripts\python.exe experiment_total_rounding_tenge_v1\run_fixture.py
```

**2. Предпросмотр патча**

```powershell
.\.venv\Scripts\python.exe experiment_total_rounding_tenge_v1\install.py --preview
```

Проверить `data/output/receipt_total_rounding/preview.diff`. Если текущая версия `App` отличается от ожидаемой — инсталлятор остановится. Не менять якоря вручную без отдельного анализа.

**3. Применение**

```powershell
.\.venv\Scripts\python.exe experiment_total_rounding_tenge_v1\install.py --apply
```

Перезапустить веб-сервер, если он был запущен: новые Python-функции не подхватятся старым процессом автоматически.

**4. Проверка ранее обработанного задания без повторного OCR**

```powershell
.\.venv\Scripts\python.exe experiment_total_rounding_tenge_v1\run_fixture.py --job-dir "web_outputs\ID_ЗАДАНИЯ"
```

**5. Обязательный тест полной системы с установленным RapidOCR на исходном фото из ZIP**

```powershell
.\.venv\Scripts\python.exe experiment_total_rounding_tenge_v1\run_fixture.py --full-ocr
```

Для полного принятия требуется: **16 отдельных товаров**, один НДС, все количества/цены из эталона, НДС `11147`, точная сумма `80812.65`, подтверждённый итог `80813.00`, VAT `match`, validation `match`. Не подставлять значения из JSON в OCR. Контрольную фотографию обрабатывает штатный `ReceiptPipeline`, а JSON используется **только для сравнения результатов**.

**6. Откат**

```powershell
.\.venv\Scripts\python.exe experiment_total_rounding_tenge_v1\install.py --restore
```

Установщик сверяет SHA256 перед откатом; если другой агент изменил файл после установки, откат остановится во избежание потери его работы. При применении резервные копии находятся в `data/output/receipt_total_rounding/backups/`. Все отчёты в `data/output/receipt_total_rounding/`, не в корне.

## Критерии приёмки и ограничения

- Контрольный чек на исходной фотографии проходит **все** проверки после OCR, а не только арифметику эталонного JSON;
- регрессионные тесты ранее прочитанных реальных чеков и синтетические негативные тесты проходят;
- ошибка на целый тенге без дробных строк **не принимается**;
- если напечатан дробный итог, совпадение с *округлённой целой* суммой не принимается;
- при пустых полях — статус `incomplete`; при неверном НДС — `vat_mismatch`;
- не изменять исходные OCR-значения, ставку НДС и конфигурацию `.env`;
- не объявлять полную приёмку без запуска проекта с настоящей ONNX-моделью.
