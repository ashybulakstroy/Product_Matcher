# Matching Product MVP

Проект предназначен для подбора аналогов товара по двум входным источникам:

1. Торгсофт чек — список позиций из чека / фискального документа.
2. Остатки товаров 1С — актуальные остатки по справочнику / выгрузке 1С.

Для работы проект использует данные из родительского проекта [Prj_16_OCR](C:/Work/Projects/Prj_16_OCR), с сохранением той же структуры каталогов и подхода к хранению данных.

## Основная задача MVP

Для каждой позиции чека нужно вернуть Top-N кандидатов из остатков 1С, отсортированных по убыванию процента сходства.

## Многократные алгоритмы поиска аналогов

Система должна поддерживать несколько независимых алгоритмов поиска аналогов. Каждый алгоритм должен иметь свой уникальный идентификатор и общую схему представления результатов.

Требования:

1. Каждый алгоритм должен иметь свой идентификатор, например `copilot_1`.
2. Результаты поиска по каждому алгоритму выводятся отдельно на странице тестирования.
3. На основной странице отображается только лучший кандидат, найденный этим алгоритмом.
4. В таблице №1 должна быть колонка с идентификатором алгоритма и ссылкой на полный список кандидатов по этому алгоритму.
5. В таблице №2 показывается первый кандидат с недостаточным количеством товаров для этого алгоритма.
6. В таблице №2 также должно показываться имя алгоритма, который предложил этого кандидата, с ссылкой на полный список кандидатов по этому алгоритму.
7. Добавление нового алгоритма выполняется через основную страницу конфигурации алгоритмов.
8. Текущий рабочий алгоритм называется `copilot_1`.

Формат данных для API должен включать:

```json
{
  "algorithm_id": "copilot_1",
  "best_candidate": {"stock_id": "s1", "stock_name": "Молоко ...", "similarity_pct": 96.7},
  "results_by_algorithm": [
    {
      "algorithm_id": "copilot_1",
      "algorithm_name": "copilot_1",
      "items": [
        {
          "candidates": [],
          "excluded_candidates": []
        }
      ],
      "best_candidate": {},
      "low_stock_candidate": {}
    }
  ]
}
```

В текущем коде используется алгоритм `copilot_1` как основной и обязательный идентификатор для тестирования и веб-проверки.

## SQL STR 3

На `/analog` доступен `sql_str_3` рядом с `sql_str_2` и `copilot_1`.
Версия 3 учитывает редкость слов в текущем каталоге, сравнивает слова целиком
с ограниченным допуском опечаток, отдельно проверяет модели и числовые признаки.
Масса, объём и длина приводятся к общим единицам (`2,5 кг` = `2500 г`).
Отличающиеся характеристики снижают оценку; отсутствующие получают меньший штраф.
В полном списке показаны причины оценки. Процент является рейтингом, а не
вероятностью правильного соответствия. Синонимы, сложные размерные цепочки
и смысловая взаимозаменяемость пока требуют отдельной доработки.
Качество на проверенной пользователем выборке ещё не измерено.


В формах главной страницы и `/analog` можно задать цену за единицу.
Для всех трёх алгоритмов при одинаковом `similarity_pct` кандидаты сортируются
по абсолютному отклонению цены, до ограничения Top-N и с учётом остатков.
Источник цены каталога — `accounting_price` (учётная цена 1С), не цена продажи.
Цены должны относиться к одинаковой валюте, единице и налоговой основе;
автоматического пересчёта НДС, валюты или фасовки этот критерий не выполняет.
Пустая цена запроса сохраняет прежний порядок. Кандидаты без цены при равных
процентах идут после кандидатов с известной ценой. Нулевая цена допустима.
Цена используется только для ранжирования; цены чека и счёта не изменяются.


## OpenCode 4

`opencode_4` доступен на главной и `/analog`, включён в сравнение всех алгоритмов.
Реализация: `App/matching/algorithms/hybrid/opencode_4.py`. Основа — идеи исследований
`C:/Temp/OpenCodeTest/opencode/analyze_failure_causes.py`, `analyze_brand_color.py`
и примеры `failure_causes.txt`; готового алгоритма в источнике не было.
Новая реализация использует взвешенное сравнение слов и отдельные проверки
вида товара, полного артикула, модели/серии, размерных цепочек, цвета и марки.
Размеры с указанными единицами приводятся к общей шкале. Причины оценки
передаются в `match_reasons`. Цена разрешает равные баллы через общий слой API.
Словари видов, марок и цветов ограничены; нераспознанная характеристика
не является доказательством совпадения. Однобуквенные цвета не угадываются.
Справочник с предварительными предложениями не используется как обучение
или подтверждённая разметка. Превосходство на проверенной выборке не измерено.

## Semantic 5 — смысловой поиск без SQL

`semantic_5` включён в общее сравнение на главной странице и `/analog`.
Он использует локальную ONNX-модель `multilingual-e5-small` (квантованная
версия `Xenova/multilingual-e5-small`, MIT) на процессоре. PyTorch, SQL,
векторный сервер и облачный API для поиска не требуются.

На новом компьютере после установки зависимостей подготовьте модель и каталог:

```powershell
.\.venv\Scripts\python.exe -m pip install -r requirements.txt
.\.venv\Scripts\python.exe -m App.semantic_setup
.\.venv\Scripts\python.exe -m App.web_server
```

Только команда подготовки загружает файлы из Hugging Face: около 135 МБ.
Версия модели закреплена, SHA-256 обоих файлов проверяются перед использованием.
Данные товаров при поиске не отправляются в интернет. После подготовки
поиск работает без подключения к сети.

Модель и NumPy-кэш находятся в `.cache/semantic_5/` и не входят в Git.
Для каждого набора названий сохраняется отдельный файл `catalog-<hash>.npz`.
Изменение названий, их порядка или версии модели автоматически создаёт новый
кэш. Изменение цены и остатков не требует повторного расчёта векторов;
в результатах используются текущие значения. Старые файлы кэша можно удалить
при остановленном сервере — они восстановятся при следующем поиске.

Итоговая оценка — косинусная близость векторов с поправками за несовпадение
характеристик из `opencode_4`. Совпадения слов для попадания в кандидаты не
требуются. В полном списке показываются исходная смысловая близость и причины
снижения оценки. Цена разрешает равные итоговые оценки по общему правилу.
Близость E5 не является вероятностью совпадения и не калибрована относительно
процентов других алгоритмов; связанные по смыслу товары могут оказаться
невзаимозаменяемыми. Качество на проверенной товарной выборке ещё не измерено.

Для коротких неоднозначных названий предусмотрены явные раскрытия
«болгарка/УШМ» → «угловая шлифовальная машина», «водоэмульсионка» →
«краска водоэмульсионная», «пена для монтажа» → «пена полиуретановая монтажная».
Уточнение отображается в причинах оценки, характеристики запроса сохраняются.
Если модель отсутствует или не загружается, интерфейс показывает причину,
а остальные алгоритмы продолжают работать.

## Пакет matching и параллельное выполнение

Тринадцать алгоритмов и общий слой их выполнения находятся в `App/matching/`:

```text
App/matching/
├── contracts.py         # Общие структуры результата и описания алгоритма
├── registry.py          # Единственный реестр для выполнения, API и интерфейса
├── engine.py            # Запуск, изоляция ошибок, время и результаты
├── cpu_executor.py      # Постоянный пул до четырёх CPU-процессов
├── ranking.py           # Цена, остатки, Top-N и полный список
├── attributes.py        # Размеры, модели, артикулы, цвет и марка
├── normalization.py
├── token_scoring.py
├── cache.py             # Кэш полных результатов для ссылок
├── worker.py
└── algorithms/
    ├── fuzzy/copilot_1.py
    ├── lexical/sql_str_2.py
    ├── lexical/sql_str_3.py
    ├── hybrid/opencode_4.py
    └── semantic/
        ├── e5.py        # semantic_5 и файловый кэш векторов
        ├── model.py     # Загрузка и локальное выполнение E5 ONNX
        ├── extra_runtime.py
        ├── rubert_12.py
        └── minilm_13.py
```

В `App/services/` оставлены совместимые импорты прежних имён; исходные формулы,
идентификаторы и оценки алгоритмов сохранены. OCR и штатное формирование счетов
используют прежнюю логику родительского приложения.

Параллельный запуск включён по умолчанию. Текстовые алгоритмы выполняются
в пуле до четырёх CPU-процессов, E5 — одновременно с ними в отдельном потоке с одной
общей моделью и собственными CPU-потоками ONNX. Пулы повторно используются
между HTTP-запросами. Порядок строк результатов определяется выбором
алгоритмов, а не порядком завершения задач. Сбой одного алгоритма показывается
отдельно и не удаляет результаты остальных.

В «Настройках поиска» страницы `/analog` можно отключить параллельный режим
для сравнения. API принимает `parallel: false`; без этого поля используется
`true`. Ответ содержит `execution_mode`, общее `elapsed_ms` и `elapsed_ms`
каждого алгоритма. Время алгоритма включает его подготовку/поиск внутри
исполнителя; общее время дополнительно включает очередь, передачу данных
и итоговую сортировку. Первый запуск может быть медленнее из-за создания
процессов, загрузки модели и подготовки векторов.

`GET /api/matching/algorithms` отдаёт реестр и режим по умолчанию.
Для добавления алгоритма реализуйте функцию с контрактом
`(checked_products, stock_products, top_n) -> list[dict]`, добавьте описание
в `registry.py` и перезапустите сервер. Веб-обработчики менять не нужно.

Поиск и импорт модулей не скачивают веса и не требуют SQL или PyTorch.

Для MiniLM на новом компьютере:

```powershell

```

Для RuBERT нужен разовый экспорт из официальных Safetensors. Рекомендуется
отдельное окружение; CPU-версия PyTorch не устанавливается в среду веб-сервера:

```powershell

.\.cache\semantic_extra\setup_env\Scripts\python.exe -m pip install torch --index-url https://download.pytorch.org/whl/cpu
.\.cache\semantic_extra\setup_env\Scripts\python.exe -m pip install -r requirements-setup-rubert.txt
.\.cache\semantic_extra\setup_env\Scripts\python.exe -m App.semantic_extra_setup --model rubert --self-test
```

После подготовки обе модели можно проверять обычным проектным Python без Torch:

```powershell
.\.venv\Scripts\python.exe -m App.semantic_extra_setup --model all --self-test
```

Ревизии моделей закреплены полными SHA коммитов. MiniLM сверяется с известными
SHA-256, экспорт RuBERT создаёт проверяемый манифест весов и токенизатора.
Экспорт использует `trust_remote_code=False` и CPU attention `eager`.
Проверяются размерности, нормализация, CLS/mean pooling, офлайн-поиск,
повторное использование кэша и работа остальных алгоритмов при недоступной модели.

Названия передаются новым моделям без словаря раскрытий `semantic_5` — поведение
пакета сохранено для независимого сравнения. На проверенном коротком запросе
«болгарка» обе модели предложили другие виды товаров; на развёрнутом названии
садовой тачки обе вывели тачки. Это функциональная проверка, а не измерение
точности на подтверждённом корпусе; высокая близость не доказывает соответствие.

## Таблица 0.5 — голосование алгоритмов

На `/analog` перед таблицей №1, а на главной перед сравнением алгоритмов,
показывается таблица голосования по правилам `R:/Torgsoft_1C_Voting_V1`.
Каждый успешно завершившийся алгоритм отдаёт максимум один голос за
`items[*].best_candidate` после общей фильтрации по остаткам и ранжирования.
Голоса подсчитываются отдельно для каждой позиции чека; кандидаты объединяются
по строковому коду 1С с сохранением ведущих нулей. Дефицитные кандидаты,
ошибки и отсутствие результата не участвуют.

Доля голосов считается от числа реально проголосовавших алгоритмов.
При равенстве голосов у лидеров победитель не назначается. Радиокнопка
только отмечает предварительный выбор в текущем браузере и формирует событие
`product-matcher:vote-selection`; сохранения, обучения и записи в 1С нет.
Новый поиск сбрасывает этот выбор.

Дополнительные поля API: `voting.positions` и `voting_elapsed_ms`.
Оценки алгоритмов и прежний `best_candidate` не изменены. Модуль
`App/matching/voting.py` обрабатывает уже готовые результаты без повторного
поиска. Общий компонент обеих страниц — `App/web/voting.js`; цены и отклонения
отображаются в принятом формате целых значений.

## Дополнительная проверка чисел OCR

Ансамбль числового OCR использует RapidOCR, NumPy, OpenCV и python-dotenv
из рабочего окружения `.venv`; они перечислены в `requirements-web.txt`.

`OCR_NUMERIC_ENSEMBLE_TESSERACT_EXE` в корневом `.env`.
При недоступности движка сохраняется штатная повторная проверка OCR.

EasyOCR по умолчанию выключен и для текущей работы не требуется.
Папка `data/output/ocr_numeric_ensemble` содержала временные материалы испытаний;
рабочее приложение от неё не зависит. Визуальные отчёты экспериментов хранятся
в `experiment_outputs`, отдельно от рабочих библиотек.

## Допуск при проверке НДС

Проверка в `App/ocr/receipt_math.py` (`verify_vat`) сравнивает сумму налоговых
строк с расчётной `taxable_base × ставка / 100` с учётом напечатанной точности
(целые тенге или копейки). Разница строго меньше 1 ₸ — максимум 0,99 ₸ —
считается допустимой законодательной погрешностью округления. В этом случае
статус НДС остаётся `match`, строка НДС не переводится в `needs_review`, а
фактическая разница, `tolerance` и `within_tolerance` сохраняются в
`calculation.vat` для аудита. Разница 1 ₸ и более остаётся `mismatch`.
Проверка общей суммы чека выполняется отдельно и по-прежнему требует точного
совпадения.

## Ранняя проверка товарной таблицы

Перед распознаванием товаров `App/ocr/table_verification.py` проверяет найденную
область по двум признакам: относительным пропорциям четырёх столбцов и первой
строки сетки, а также подписям заголовка на казахском или русском языке.
Подписи должны относиться к разным столбцам и находиться на одной строке.
Используется тот же локальный RapidOCR; отдельные модели не устанавливаются.
Размеры проверяются относительно ширины таблицы, без привязки к пикселям фото.

Нечитаемый заголовок не отвергает таблицу с подтверждённой геометрией.
При неопределённой проверке сохраняется прежний результат детектора.
При отсутствии границы или явном ложном объекте дополнительный fallback
`recover_compact_table` ищет короткую таблицу внутри области бумаги на двух
масштабах. Он не заменяет существующие проходы для длинных чеков и принимает
только независимо проверенный кандидат. Контур бумаги сам по себе недостаточен.

Диагностика решения и дополнительные обращения к OCR заголовка записываются
в `table_verification.json` рядом с результатами задания в `web_outputs`.
Подтверждение области таблицы не отменяет отдельной проверки суммы и НДС.

## Выборочное восстановление названий

`App/ocr/selective_text_recovery.py` сначала повторно собирает имя из OCR-блоков,
попадающих в ту же ячейку. Для оставшихся подозрительных названий читает только
ячейку имени двумя вариантами RapidOCR и Tesseract. По умолчанию проверяются
не более трёх строк на чек. Низкое сходство с каталогом само по себе не является
поводом для повторного OCR. Каталог не используется как источник восстановленного текста.

Исходные `name_raw`, `raw_lines`, количества и цены сохраняются. Подтверждённый
текст записывается в `name_recovered` и используется в последующем сопоставлении.
Конфликт обозначений модели, отсутствие согласования движков или ошибка чтения
сохраняют исходное имя. Подтверждённые пользователем имена защищены.

Настройки в корневом `.env`: `OCR_TEXT_RECOVERY_ENABLED` (по умолчанию `1`),
`OCR_TEXT_RECOVERY_MAX_ROWS` (`3`), `OCR_TEXT_RECOVERY_MIN_CONFIDENCE` (`0.60`),
`OCR_TEXT_RECOVERY_LANG` (`rus+eng`), `OCR_TEXT_TESSERACT_EXE` (необязательный путь
к установленному движку). Установка языковых весов описана в
`models/tesseract/README.md`. Дополнительных Python-библиотек не требуется.

Диагностика — `web_outputs/<job>/selective_text_recovery.json`, фрагменты
изображений — `web_outputs/<job>/text_recovery/`. Рабочий модуль не зависит
от исходной папки эксперимента и `data/output`. Повторное чтение не гарантирует
восстановления: на проверенном оригинале строки №12 движки разошлись в букве
обозначения модели, поэтому автоматическая замена не принята.

## Перенос распознанных ячеек в электронный чек

Промежуточные `draft_rows` содержат `ready_cells`: ячейки, для которых обработаны
все обнаруженные текстовые блоки. Незавершённая строка многострочного имени не
считается готовой ячейкой. Эта проверка использует уже полученные блоки OCR и не
запускает дополнительных движков.

Интерфейс запускает отдельный перелёт каждой готовой ячейки без интервального
таймера, допускает несколько одновременных перелётов и открывает значение в
ячейке назначения после приземления. Итоговая галочка и редактор появляются
после завершения перелётов. Конечная точка всегда находится внутри настоящей
ячейки чека; новые загрузки отменяют старые анимации. При уменьшении движения
или скрытой вкладке значения появляются без перелётов.

## Повреждённая короткая таблица чека

`App/ocr/damaged_receipt_geometry.py` добавляет резервный поиск по реально
сохранившимся пяти вертикальным границам и горизонтальным линиям, без OCR.
Успешная исходная таблица сохраняется. Сомнительный правый фрагмент заменяется
только при подтверждённой полной сетке, совпадении области и независимом
признаке разрыва в колонке названия. Детектор рассчитан на короткие таблицы
в средней части фотографии; произвольные повреждения он не гарантирует.

Для восстановленной сетки применяется безопасный поворот, а сохранившиеся
полные разделители задают строки и отделяют нижнюю ячейку итога. Для до трёх
товаров `damaged_receipt_text.py` проверяет узкую светлую полосу с печатным
текстом по обеим сторонам. Только затронутые строки передаются существующему
ограниченному повторному OCR названия. Исходные OCR-блоки и числовые поля
сохраняются; утраченные буквы не достраиваются, математика проверяется как раньше.

Диагностика задания: `damaged_grid_recovery.json`, `damaged_row_layout.json`
(если восстановлена сетка), `damaged_name_stripe.json` и обычный отчёт повторного
чтения. Новых зависимостей нет. Приложение не зависит от папки эксперимента
или `data/output`; контрольные прогоны и HTML-отчёт размещаются в
`experiment_outputs/experiment_damaged_receipt_recovery_v1/`.

## Изогнутая сетка чека V2

`App/ocr/grid_curvature_v2.py` — независимый детектор согласованного изгиба
горизонтальных печатных линий и кандидат выпрямления. Он не запускает OCR и не
обращается к внешним сервисам. V2 рассматривается только как резерв после
проверенного контура и волновой сетки: существующий `wave_grid` всегда имеет
приоритет, а ранний отказ `dewarp_necessity=SKIP` сохраняется.

Кандидат принимается, если исходная область таблицы имеет решение `DEWARP`,
после выпрямления изгиб больше не подтверждается, найдены минимум четыре
горизонтальные границы строк и деформация имеет безопасный якобиан. Для
горизонтального варианта x-координаты колонок переносятся из проверенной
контурной разметки, границы строк берутся из выпрямленных линий V2, а результат
дополняется теми же 16 px полями, что и остальные методы. Служебные поля:
`grid_curvature` (диагноз исходной области), `grid_curvature_candidate`
(полный отчёт кандидата) и `grid_curvature_assessment` (причина выбора или
отказа).

Переключатель: `OCR_GRID_CURVATURE_V2=select` (по умолчанию) включает выбор
кандидата, `shadow` только записывает диагностику и сохраняет прежний результат,
`off` полностью отключает V2. Проверка на 13 реальных чеках: на `curved`
устранено слияние цены строки НДС с итогом и арифметика сошлась
(`63684.00`), на `extra_sixteen` улучшено распознавание названий без изменения
итога; на остальных источниках строки, итоги и НДС не изменились. Повторный
прогон: `experiment_outputs/grid_curvature_v2/regression.py`, результаты — в
`experiment_outputs/grid_curvature_v2/comparison.json` и
`experiment_outputs/grid_curvature_v2/regression.md`.

## Лексические алгоритмы BM25 14 и TF-IDF 15

В общий реестр добавлены `bm25_14` (Okapi BM25 с весами редких слов и поправкой
на длину названия) и `tfidf_15` (косинусная близость TF-IDF по словам и
символьным фрагментам длиной 3–5). Второй допускает небольшие опечатки, но оба
остаются лексическими алгоритмами и не заменяют смысловой поиск.

Они доступны на `/analog`, выполняются в CPU-процессах и участвуют в обычном
голосовании. Проверки характеристик, цены и остатков используют существующие
общие правила. Индексы кэшируются в памяти каждого процесса по названиям
каталога; изменение цены, остатка или кода не возвращает устаревшие данные.
Новых зависимостей, моделей и SQL не требуется. Исходная папка эксперимента
для работы приложения не нужна. Точность на подтверждённых парах отдельно
не измерена; проверка на запросах по каталогу подтверждает работоспособность.
